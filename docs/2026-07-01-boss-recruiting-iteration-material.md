# Boss 招聘助手需求迭代材料

## 1. 背景

当前项目已经完成第一版交付，核心链路能够跑通：

- 本地 macOS App 启动 Dashboard。
- 通过 Chrome CDP 控制已登录 Boss 招聘端页面。
- 按岗位处理沟通页并发送索简历话术。
- 按岗位处理推荐牛人页并打招呼。
- 收取附件简历并保存到本地。
- 根据岗位路由同步到飞书招聘。

第一版验证了自动化链路可行，但在 HR 真实使用后暴露出几个需要进入下一轮迭代的问题：

1. 岗位配置仍然偏人工，岗位标识、Boss 岗位别名、飞书招聘岗位 ID 都需要 HR 或交付人员维护。
2. 岗位唯一性不够强，存在类似 `AAABB` 和 `AAABBCC` 的包含关系时，可能误匹配。
3. 候选人初筛能力不足。部分岗位候选人量很大，可能有几千份简历或推荐候选人，需要先按岗位画像过滤，再进入打招呼或后续跟进。
4. 飞书岗位 ID 获取门槛较高，HR 不容易自行找到和维护。

本材料用于沉淀本轮需求变更范围和建议实现路径，后续再基于本文档拆分具体开发计划。

## 2. 本轮迭代目标

本轮目标不是增加更多自动化动作，而是提升自动化的准确性和可配置性。

优先级从高到低：

1. **岗位匹配安全性优先**：岗位关键词匹配改为精确匹配，避免打错岗位。
2. **岗位配置简化**：减少 HR 手动填写字段，尤其是岗位标识和岗位 ID。
3. **岗位画像初筛**：基于 Boss 已有筛选面板或页面字段，先过滤候选人池，再执行打招呼。
4. **保留可回滚能力**：每一项改动都应独立可测、可开关，避免影响已跑通主链路。

## 3. 现状问题分析

### 3.1 岗位关键词匹配过宽

当前代码中，岗位匹配主要依赖归一化后的包含判断。

相关位置：

- `config/job-router.cjs`
- `boss-loop/boss_lite_screen_and_greet.mjs`
- `orchestrator/recommend_greet_runner.mjs`
- `boss-loop/collect_visible_resumes.js`

典型逻辑为：

```js
normalizedText.includes(alias)
```

这会导致：

```text
DSP运营经理
```

被判断为包含：

```text
DSP运营
```

在真实招聘场景中，这两个岗位可能职责、薪资、经验要求完全不同。该问题属于高风险问题，因为它会直接导致：

- 沟通页切错 Boss 岗位筛选。
- 推荐牛人页切错岗位。
- 候选人归档到错误岗位。
- 后续飞书同步进入错误岗位。

### 3.2 岗位配置仍需要较多人工理解

当前岗位配置字段包括：

- 岗位标识 `job_key`
- 岗位名称 `display_name`
- Boss 岗位别名 `boss_job_names`
- 飞书招聘岗位 ID `feishu_hire_job_id`
- 启用状态 `enabled`

其中 `job_key` 和 `feishu_hire_job_id` 对 HR 不直观：

- `job_key` 是系统内部稳定标识，HR 容易填写中文或重复。
- `feishu_hire_job_id` 需要从飞书招聘后台或接口中获取，普通 HR 不容易拿到。

### 3.3 缺少岗位画像过滤

目前系统主要在页面候选人列表中逐个读取、判断、打招呼。对于候选人数量很大的岗位，这种方式效率不够。

业务希望先按岗位画像过滤，例如：

- 学历要求：不限、本科及以上、硕士及以上、博士。
- 院校要求：不限、统招本科、双一流、211、985、留学生、QS 100、QS 500。
- 经验要求：不限、在校/应届、25年毕业、26年毕业、26年后毕业、1-3年、3-5年、5-10年。
- 年龄要求：不限、20-25、25-30、30-35、35-40、40-50、50以上。
- 性别要求：不限、男、女。
- 薪资区间。
- 活跃度。
- 跳槽频率。
- 求职状态。
- 职位要求。

这些条件与 Boss 页面现有筛选面板接近，因此可以优先考虑“驱动 Boss 原生筛选面板”，而不是从零实现一套独立筛选引擎。

## 4. 方案概览

### 4.1 岗位匹配规则：从包含匹配改为精确匹配

建议将岗位匹配规则统一收紧为“精确匹配 + 明确边界匹配”。

#### 基础规则

将文本归一化后进行比较：

- 去除空格、部分标点、全角半角差异。
- 保留岗位名主体。
- 不允许岗位名直接包含另一个岗位名就算匹配。

示例：

| 页面文本 | 配置岗位 | 当前结果 | 新规则结果 |
| --- | --- | --- | --- |
| DSP运营 | DSP运营 | 匹配 | 匹配 |
| DSP运营经理 | DSP运营 | 误匹配 | 不匹配 |
| DSP运营经理 | DSP运营经理 | 匹配 | 匹配 |
| DSP运营 _ 南京 8-12K | DSP运营 | 匹配 | 匹配 |
| DSP运营经理 _ 南京 15-25K | DSP运营 | 误匹配 | 不匹配 |

#### 允许的边界

Boss 页面岗位文本可能带城市、薪资或分隔符，例如：

```text
DSP运营 _ 南京 8-12K
DSP运营｜南京
DSP运营 / 南京
DSP运营（南京）
```

这些可以识别为 `DSP运营`。

但以下不应识别为 `DSP运营`：

```text
DSP运营经理
DSP运营主管
DSP运营实习生
高级DSP运营
```

#### 遇到歧义时的策略

如果一个页面文本同时可能对应多个岗位，不自动选择。

建议结果为：

```text
岗位匹配存在歧义，请检查岗位配置或 Boss 页面岗位名称。
```

系统应暂停或跳过，而不是继续发送。

### 4.2 岗位配置简化

岗位配置简化分为两个方向：自动生成内部标识、自动获取或导入外部岗位 ID。

#### 4.2.1 岗位标识自动生成

现状：

HR 需要填写 `job_key`，例如：

```text
customer_service_operations
```

建议改为：

1. HR 只填写或选择岗位名称。
2. 系统自动生成 `job_key`。
3. 若岗位名称重复，自动追加短编号。
4. 保存后 `job_key` 不在普通界面突出展示，只作为高级信息保留。

示例：

```json
{
  "job_key": "job_20260701_001",
  "display_name": "DSP运营",
  "boss_job_names": ["DSP运营"]
}
```

优点：

- HR 不需要理解内部标识。
- 避免中文、重复、非法字符导致保存失败。
- 后续可稳定用于本地目录、状态文件和同步队列。

注意：

- 已保存岗位的 `job_key` 不应随岗位名称变化而变化。
- 如果 HR 修改岗位名称，只修改展示名和别名，不重建 `job_key`。

#### 4.2.2 Boss 岗位信息自动拉取

可以尝试通过脚本从 Boss 页面读取岗位列表。

目标：

- 从沟通页岗位筛选下拉中读取所有岗位。
- 从推荐牛人页岗位切换下拉中读取所有岗位。
- 自动生成待配置岗位列表。
- HR 只需要选择需要启用的岗位，并补充飞书同步信息。

建议入口：

```text
岗位配置 -> 从 Boss 页面读取岗位
```

读取结果示例：

```json
[
  {
    "boss_job_name": "DSP运营",
    "source": "chat_filter"
  },
  {
    "boss_job_name": "DSP运营经理",
    "source": "chat_filter"
  }
]
```

系统写入配置时：

```json
{
  "job_key": "job_20260701_001",
  "display_name": "DSP运营",
  "boss_job_names": ["DSP运营"],
  "enabled": true
}
```

风险：

- Boss 页面结构可能变化。
- 需要 HR 已登录 Boss，并打开正确页面。
- 不同企业账号页面字段可能不同。

因此该能力建议作为“辅助导入”，而不是唯一配置方式。

#### 4.2.3 飞书岗位 ID 简化

飞书招聘岗位 ID 暂时不能直接去掉，因为同步飞书招聘时仍需要明确目标岗位。

本轮讨论后，建议采用“内置预设 + 自动生成 job_key + 飞书接口拉取岗位列表”的组合方案。

#### 内置预设岗位

大部分常用岗位可以由交付包内置预设，例如：

```json
{
  "display_name": "产品运营",
  "boss_job_names": ["产品运营"],
  "profile_filters": {}
}
```

HR 首次打开时可以从预设岗位中启用，而不是从零新增。

预设岗位可以包含：

- 岗位名称。
- Boss 岗位名。
- 默认画像筛选条件。
- 常见话术模板。

预设岗位不强制写死飞书岗位 ID。飞书岗位 ID 可以后续通过飞书接口选择或手动补充。

#### 新增岗位保留配置能力，但简化字段

当出现预设外的新岗位时，仍保留新增岗位能力，但 HR 只需要填写：

1. Boss 岗位名。
2. 飞书招聘岗位，优先从接口拉取列表中选择；必要时可手动填写飞书岗位 ID。

系统自动生成并维护：

- `job_key`
- `display_name`
- `boss_job_names`
- 本地简历目录名
- 同步队列路由字段

岗位配置页不再要求 HR 理解 `job_key`。`job_key` 可以作为高级字段隐藏，只在排查问题时展示。

#### 通过飞书开放平台接口拉取岗位列表

你已经用测试账号确认飞书开放平台岗位列表权限可用，因此飞书岗位简化应优先走接口方案。

建议 Dashboard 增加：

```text
刷新飞书岗位列表
```

系统调用飞书招聘岗位列表接口后，展示岗位名称、岗位状态和岗位 ID。HR 在新增或编辑岗位时，直接从下拉框选择飞书岗位。

配置保存后仍落到内部字段：

```json
{
  "feishu_hire_job_id": "123456789"
}
```

但 HR 感知上是选择“飞书岗位名称”，不是复制长数字 ID。

#### 保留手动填写作为兜底

虽然接口权限已验证可用，仍建议保留手动填写飞书岗位 ID 的兜底入口，原因：

- 飞书接口可能临时失败。
- 某些企业账号权限可能不一致。
- 交付现场需要快速绕过接口异常。

因此最终交互建议：

```text
飞书岗位：下拉选择
无法找到？手动填写岗位 ID
```

### 4.3 岗位画像过滤

岗位画像过滤应按 Boss 页面能力分为两条链路：推荐牛人页和沟通页。

#### 4.3.1 推荐牛人页：驱动 Boss 原生筛选面板

推荐牛人页有 Boss 自带筛选面板。该页面的画像初筛应优先复用 Boss 原生能力。

推荐方案：

1. HR 在本地 Dashboard 中为岗位配置筛选条件。
2. 系统启动推荐页任务时，打开 Boss 推荐牛人页。
3. 脚本点击 Boss 页面右上角“筛选”。
4. 根据 Dashboard 配置，模拟点击或拖动 Boss 原生筛选控件。
5. 确认筛选条件生效后，再读取推荐候选人并打招呼。

推荐页第一阶段建议支持：

- 学历要求。
- 院校要求。
- 经验要求。
- 年龄要求。
- 活跃度。
- 求职状态。
- 性别要求。

其中年龄属于滑块或范围控件，需要单独处理。建议实现时优先支持 Boss 页面常见固定年龄段；自定义拖动作为第二步。

推荐页暂不建议第一阶段自动处理：

- 薪资区间自定义滑块。
- 复杂自定义滑块。
- 多个组合条件的高级逻辑。
- VIP 专享或不同账号不一定出现的筛选项。

原因：

- 滑块类 UI 容易受窗口尺寸和缩放影响。
- 不同 Boss 账号可见筛选项可能不同。
- 复杂组合容易增加误操作风险。
- 第一阶段目标是把几千候选人先缩小到更合理范围，不追求一次做到完全精准。

#### 4.3.2 沟通页：本地逐人过滤

沟通页没有 Boss 自带的画像筛选面板，不能像推荐页一样先统一应用筛选条件。

沟通页应采用“逐人打开 + 本地过滤”的方式。

可用字段来自沟通页候选人详情区域，例如截图中的：

```text
汪书媛 · 在线 | 24岁 | 28年应届生 | 硕士
哈尔滨工业大学 · 建筑 · 硕士
期望职位
沟通职位
```

沟通页过滤流程建议：

1. 按岗位切换 Boss 沟通页岗位筛选。
2. 读取当前页候选人卡片。
3. 点开候选人。
4. 从详情头部和教育经历中提取年龄、学历、毕业年份、院校。
5. 与岗位画像条件进行本地判断。
6. 不满足条件则跳过，并记录原因。
7. 满足条件才进入后续打招呼或索简历。

例如：

- 候选人年龄是否在范围内。
- 学历是否满足要求。
- 学校是否满足院校层级。
- 毕业年份是否符合应届/经验要求。
- 是否应届。

沟通页本地过滤的好处：

- 可记录跳过原因。
- 可解释为什么没有打招呼。
- 不依赖 Boss 是否提供筛选面板。

局限：

- 需要逐个点开候选人，速度比推荐页原生筛选慢。
- 页面字段解析不一定完整。
- 院校层级判断需要本地规则或院校名单支持。

建议输出日志：

```json
{
  "candidate_name": "张三",
  "job_key": "dsp_operations",
  "filter_result": "skipped",
  "reason": "age_out_of_range",
  "expected": "20-25",
  "actual": "28"
}
```

#### 4.3.3 推荐页和沟通页共享同一套岗位画像配置

Dashboard 中 HR 只配置一套岗位画像。执行时按页面类型分流：

- 推荐牛人页：优先映射到 Boss 原生筛选面板。
- 沟通页：用本地解析字段做逐人过滤。

如果某个条件在推荐页可由 Boss 原生筛选完成，在沟通页也需要本地实现同等判断，避免同一岗位在两个页面标准不一致。

#### 岗位画像配置结构建议

建议在岗位配置中增加 `profile_filters` 字段：

```json
{
  "job_key": "job_20260701_001",
  "display_name": "DSP运营",
  "boss_job_names": ["DSP运营"],
  "profile_filters": {
    "education": "bachelor_or_above",
    "school": ["regular_bachelor", "double_first_class"],
    "experience": ["fresh_graduate", "one_to_three_years"],
    "age": {
      "min": 20,
      "max": 30
    },
    "activity": "active_recent_week",
    "job_status": ["actively_looking", "open_to_opportunities"]
  }
}
```

Dashboard 中可以做成中文选项：

```text
学历要求：不限 / 本科及以上 / 硕士及以上 / 博士
院校要求：不限 / 统招本科 / 双一流 / 211 / 985 / 留学生 / QS100 / QS500
经验要求：不限 / 在校应届 / 1-3年 / 3-5年
年龄要求：不限 / 20-25 / 25-30 / 自定义
```

## 5. 分期建议

### Phase 1：安全修复，岗位精确匹配

目标：

- 解决 `AAABB` 和 `AAABBCC` 误匹配问题。
- 防止真实打招呼发错岗位。

范围：

- 改造 `config/job-router.cjs`。
- 改造沟通页岗位筛选匹配逻辑。
- 改造推荐页岗位筛选匹配逻辑。
- 改造收简历阶段岗位校验逻辑。
- 增加测试用例：
  - `DSP运营` 不匹配 `DSP运营经理`。
  - `DSP运营 _ 南京 8-12K` 匹配 `DSP运营`。
  - 相似岗位同时存在时，歧义直接暂停或跳过。

验收标准：

- 选择 `DSP运营` 时不会进入 `DSP运营经理`。
- 选择 `DSP运营经理` 时不会进入 `DSP运营`。
- 推荐页和沟通页都适用。
- 匹配失败时不发送消息。

### Phase 2：岗位配置简化

目标：

- HR 不再手动填写岗位标识。
- 大部分常用岗位可直接从内置预设启用。
- 新增岗位时只需要填写 Boss 岗位名，并选择或填写飞书岗位。

范围：

- 增加内置岗位预设列表。
- Dashboard 支持从预设岗位启用。
- 新增岗位时自动生成稳定 `job_key`。
- 岗位配置页隐藏或弱化 `job_key`。
- 新增岗位只要求填写 Boss 岗位名。
- 增加相似岗位提醒。

验收标准：

- HR 可以不手填 `job_key`。
- HR 可以从预设岗位快速启用常用岗位。
- 新增岗位保存后自动生成稳定 `job_key`。
- 相似岗位不会互相覆盖。
- 已保存岗位再次编辑不会改变 `job_key`。

### Phase 3：Boss 岗位自动读取

目标：

- 辅助 HR 从 Boss 页面读取岗位名称，减少手工录入错误。

范围：

- Dashboard 新增“从 Boss 页面读取岗位”按钮。
- 后端新增读取 Boss 岗位列表 API。
- 从沟通页岗位筛选下拉读取岗位。
- 从推荐页岗位下拉读取岗位。
- 读取后与已有配置和预设岗位做精确去重。

验收标准：

- HR 可以从 Boss 页面导入岗位列表。
- 导入后可直接启用岗位。
- `DSP运营` 和 `DSP运营经理` 会作为两个独立岗位展示。
- 读取失败时给出清晰提示，不影响手动配置。

### Phase 4：飞书岗位路由简化

目标：

- 通过飞书开放平台接口拉取岗位列表，降低 HR 获取飞书岗位 ID 的难度。

范围：

- 后端调用飞书招聘岗位列表接口。
- Dashboard 新增“刷新飞书岗位列表”。
- 岗位配置页将“飞书岗位 ID”改为“飞书同步岗位”。
- HR 优先通过下拉框选择飞书岗位。
- 保留手动填写飞书岗位 ID 作为兜底。

验收标准：

- HR 不需要直接理解长数字 ID。
- 下拉选择后，系统仍能正确写入 `feishu_hire_job_id`。
- 飞书接口失败时，可切换到手动填写。
- 未配置飞书岗位时，Boss 流程仍可执行。

### Phase 5：岗位画像过滤

目标：

- 在打招呼前减少候选人池。
- 对大岗位先筛选出更匹配的候选人。

范围：

- Dashboard 增加岗位画像配置。
- 推荐页任务启动前应用 Boss 原生筛选条件，包括学历、院校、经验、年龄等。
- 推荐页年龄筛选支持固定区间，后续再支持自定义拖动。
- 沟通页没有 Boss 原生筛选面板，采用逐人打开详情、本地解析年龄、学历、院校、毕业年份后过滤。
- 日志记录过滤原因。

验收标准：

- 可配置学历、院校、经验、年龄等基础条件。
- 推荐页能通过 Boss 原生筛选面板先缩小候选人池。
- 沟通页能在点开候选人后按本地画像规则跳过不匹配候选人。
- 候选人被跳过时有明确原因。
- 筛选条件不满足时不打招呼。
- 筛选失败时暂停，不静默继续群发。

## 6. 建议的数据结构

建议 `jobs.json` 从纯路由配置扩展为岗位配置中心。

示例：

```json
{
  "version": 2,
  "jobs": [
    {
      "job_key": "job_20260701_001",
      "display_name": "DSP运营",
      "boss_job_names": ["DSP运营"],
      "feishu_hire_job_id": "123456789",
      "enabled": true,
      "matching": {
        "mode": "exact",
        "allow_suffix_metadata": true
      },
      "profile_filters": {
        "education": "bachelor_or_above",
        "school": ["regular_bachelor"],
        "experience": ["fresh_graduate", "one_to_three_years"],
        "age": {
          "min": 20,
          "max": 30
        },
        "activity": "active_recent_week",
        "job_status": ["actively_looking"]
      }
    }
  ]
}
```

兼容策略：

- 旧版 `version: 1` 配置继续可读。
- 缺少 `matching` 时默认使用新精确规则。
- 缺少 `profile_filters` 时视为不限制。
- 不强制 HR 一次性配置所有画像。

## 7. 风险和注意事项

### 7.1 不建议继续使用宽泛包含匹配

岗位匹配属于自动化安全边界。这里应宁可少发，也不要错发。

建议原则：

```text
匹配不确定 -> 暂停或跳过
匹配确定 -> 执行
```

### 7.2 自动拉取岗位不能完全替代人工确认

Boss 页面结构可能变化，自动拉取岗位名称后仍需要 HR 确认。

建议导入后展示：

```text
系统从 Boss 读取到以下岗位，请确认需要启用的岗位。
```

### 7.3 岗位画像筛选应先做最小可用版本

第一阶段不要追求覆盖 Boss 筛选面板所有条件，也不要把推荐页和沟通页混成一种实现。

推荐页建议先做：

- 学历。
- 院校。
- 经验。
- 年龄。

推荐页通过 Boss 原生筛选面板实现，优先使用固定选项，谨慎处理自定义滑块。

沟通页建议先做：

- 年龄。
- 学历。
- 院校。
- 毕业年份或应届状态。

沟通页通过打开候选人详情后本地解析实现。由于沟通页没有原生筛选面板，不能要求它具备推荐页一样的批量前置过滤效率。

### 7.4 删除和清理动作应保守

本轮虽然重点不是简历清理，但从真实使用反馈看，本地简历不应轻易删除。

建议默认保留本地简历，上传成功后改为“归档”而不是直接删除。

## 8. 推荐优先级

本轮建议按以下顺序推进：

1. **先修岗位精确匹配**：这是安全问题，必须先做。
2. **再做岗位配置简化和内置预设**：减少 HR 配置错误。
3. **再做 Boss 岗位自动读取**：作为新增岗位辅助能力。
4. **再做飞书岗位接口拉取**：测试账号已确认权限可用，应优先走接口选择。
5. **最后做岗位画像过滤**：推荐页和沟通页分两套执行策略，逐步验证。

## 9. 后续实施前需要确认的问题

1. 岗位精确匹配中，是否允许 `高级DSP运营` 匹配 `DSP运营`？
   - 建议不允许。
2. Boss 岗位名称是否存在固定格式，例如 `岗位名 _ 城市 薪资`？
   - 如果存在，可以作为边界匹配规则的一部分。
3. 内置预设岗位清单由谁维护？
   - 建议交付方维护默认清单，HR 只负责启用和补充飞书岗位。
4. 飞书岗位列表接口返回字段是否足够展示岗位名称、状态和 ID？
   - 测试账号已确认权限开通，实施前需要用真实企业环境再跑一次接口样例。
5. 推荐页年龄筛选第一版是否只支持固定区间？
   - 建议第一版先支持固定区间，自定义拖动放到后续。
6. 沟通页本地过滤遇到字段缺失时如何处理？
   - 建议默认跳过并记录 `profile_field_missing`，不要误发。
7. 初筛目标是筛到固定数量，还是只应用条件后继续按页面顺序处理？
   - 建议第一版只应用条件和上限，例如最多处理 200 人。

## 10. 结论

本轮迭代的核心不是“增加更多自动化”，而是让自动化更稳。

最关键的修改是岗位匹配规则收紧。只要还使用包含匹配，真实业务中就会持续出现相似岗位误命中。岗位匹配修复后，再逐步推进岗位配置简化和岗位画像筛选，整体风险会更可控。
